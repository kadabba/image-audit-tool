# Спецификация: Image Audit Tool

## Назначение

Внутренний инструмент для поиска потенциально стороннего/стокового контента (изображений) на сайтах на WordPress и MODX, визуального отбора кандидатов на удаление и безопасного удаления через WP-CLI без риска случайно снести легитимный контент.

Контекст: повторяющаяся задача при работе с сайтами, доставшимися от предыдущих подрядчиков — нужно находить и убирать изображения с непонятным происхождением (риск претензий по авторским правам, как в случае с досудебным по фото "866" на promtakelag.ru).

## Принципы

1. **Никакого полностью автоматического удаления.** Каждая картинка перед удалением требует явного визуального подтверждения человеком. Программа не может отличить чужой сток от легитимной обложки статьи по имени файла или дате.
2. **Разрыв между "выбрал" и "удалилось".** Инструмент готовит команду/список для выполнения на сервере, но не имеет прямого write-доступа к БД сайта в первой версии. Это защита от масштабной ошибки одним кликом.
3. **Один сайт — один прогон.** Не пытаться унифицировать логику поиска между MODX и WordPress, между разными темами — вместо этого гибкая система "источников" (см. ниже), которую легко расширять под новый паттерн, когда он встретится.

## Архитектура (v1)

### Backend
- Python (Flask/FastAPI) или Node.js — на усмотрение реализации
- SQLite для хранения результатов сканирования (не JSON-файлы — нужна возможность отмечать статус по каждой картинке между сессиями)
- Деплой на существующий VPS (ja4.ru)

### Frontend
- Простая веб-страница (не SPA-фреймворк, чтобы не усложнять) — HTML + минимум JS
- Галерея превью с чекбоксами вместо текстового отчёта
- Фильтры: по дате загрузки, по странице, по паттерну имени файла (например, отдельно показать всё, что похоже на featured image, отдельно — что в контенте)

## Функциональность

### 1. Сканирование сайта

Вход: URL сайта.

Источники обхода (пробовать по очереди, не полагаться только на один):
- `sitemap.xml` / `sitemap_index.xml`
- Fallback: обход по внутренним ссылкам с главной страницы (лимит страниц конфигурируется)

Для каждой найденной страницы — извлечение изображений:
- `<img src>`, `data-src`, `data-original` (lazyload-атрибуты)
- `<picture><source srcset>`
- `background-image` в inline-стилях
- Фиксация: URL картинки, страница(ы), где встречается, дата (по URL /uploads/YYYY/MM/, если применимо)

### 2. Визуальный отбор

- Плитка превью, как в текущем HTML-отчёте, но с чекбоксами
- Возможность отметить группой (например, "выбрать все с /pozharnyy-minimum/")
- Сохранение выбора между сессиями (SQLite) — не нужно каждый раз просматривать заново

### 3. Генерация списка на удаление

- Экспорт отмеченных URL в `.txt` (формат, совместимый с существующим `remove-images.php`)
- Одна кнопка — копировать в буфер обмена

### 4. Поиск по множественным источникам (расширяемо)

На основе опыта трёх прогонов известны следующие паттерны, где может сидеть картинка — каждый оформляется как отдельный "checker", который можно включать/выключать при прогоне:

| Источник | Что проверяет | Статус |
|---|---|---|
| `post_content` | Прямой `<img>` в тексте записи/страницы | Реализовано (remove-images.php) |
| Featured image | `_thumbnail_id`, с нормализацией имени файла (срез суффикса `-WxH`) | Реализовано |
| Термин-мета (категории) | `wp_termmeta` — обложки категорий/тегов | Не реализовано, известен паттерн поиска |
| Опции темы (Кастомайзер) | `wp_options` (`theme_mods_*`) | Не реализовано, известен паттерн поиска |
| Хардкод в теме | Прямой grep по файлам темы (PHP-циклы, выводящие featured image связанных записей) | Только вручную через SSH, не автоматизировано |

v1 инструмента может ограничиться первыми двумя (наиболее частые случаи), с ручным резервным процессом (SSH + grep + SQL-запросы) для остальных — так же, как делали сегодня.

### 5. Удаление (выполняется НЕ инструментом, а вручную через WP-CLI)

Существующий `remove-images.php` остаётся основным механизмом:
- dry-run по умолчанию
- `apply` как явный второй шаг
- поддержка `--skip-plugins` (нужно на практике почти всегда — сломанные плагины на старых сайтах встречаются часто)
- удаление мягкое: `<img>` из контента убирается, featured image отвязывается, физический файл в медиабиблиотеке не трогается

## Известные технические грабли (учесть при реализации checker'ов)

- WordPress хранит featured image как URL **оригинального** файла, но на странице показывается превью с суффиксом размера (`-150x150`, `-700x260` и т.д.) — сравнение имён файлов обязано срезать этот суффикс
- WordPress при редактировании изображения через встроенный редактор добавляет суффикс `-eXXXXXXXXXXXXX` к реальному файлу на диске, при этом `guid` в БД остаётся старым — сравнивать нужно по полю `_wp_attached_file`, не по `guid`
- Разные сайты — разный префикс таблиц БД (не всегда `wp_`)
- Разные сайты — разные сломанные плагины, из-за которых обычные WP-CLI команды падают с фатальной ошибкой без `--skip-plugins`
- Одна и та же картинка на странице категории/архива может быть выведена кастомным PHP-циклом в шаблоне темы, а не через стандартный WordPress-механизм — такие случаи в принципе не найти через SQL/WP-CLI, только через grep по файлам темы и последующую ручную правку шаблона

## Из скоупа v1 (сознательно не делаем сразу)

- Прямое SSH-подключение и выполнение команд с backend — рискованно, добавить только после того, как процесс отбора стабилизируется на нескольких сайтах
- Автоматическая замена картинок (генерация/подбор новых) — отдельная задача, не связанная с удалением
- Поддержка MODX — паттерны там другие (чанки, Fenom/pdoTools-парсинг), первая версия фокусируется на WordPress как более частом случае
