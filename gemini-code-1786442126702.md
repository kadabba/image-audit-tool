# Спецификация: Image Audit Tool (v1.1)

## Назначение

Внутренний инструмент для поиска потенциально стороннего/стокового контента (изображений) на сайтах на WordPress и MODX, визуального отбора кандидатов на удаление и безопасного удаления через WP-CLI без риска случайно снести легитимный контент.

**Контекст:** Повторяющаяся задача при работе с сайтами, доставшимися от предыдущих подрядчиков — нужно находить и убирать изображения с непонятным происхождением (риск претензий по авторским правам, как в случае с досудебным иском по фото "866" на promtakelag.ru).

---

## Принципы

1. **Никакого полностью автоматического удаления.** Каждая картинка перед удалением требует явного визуального подтверждения человеком. Программа не может отличить чужой сток от легитимной обложки статьи по имени файла или дате.
2. **Разрыв между "выбрал" и "удалилось".** Инструмент готовит команду/список для выполнения на сервере, но не имеет прямого write-доступа к БД сайта в первой версии. Это защита от масштабной ошибки одним кликом.
3. **Один сайт — один прогон.** Не пытаться унифицировать логику поиска между MODX и WordPress, между разными темами — вместо этого гибкая система "источников" (см. ниже), которую легко расширять под новый паттерн, когда он встретится.

---

## Архитектура (v1)

### Backend
- **Язык/Фреймворк:** Python (FastAPI или Flask).
- **База данных:** SQLite (для локального хранения результатов сканирования и статусов разбора между сессиями). **Режим WAL:** `PRAGMA journal_mode=WAL` для поддержки параллельных чтения/записи (сканирование фоновое, UI работает одновременно).
- **Прокси-модуль (CORS Fix):** Встроенный эндпоинт `/proxy-image?url=...` для скачивания и отдачи превью на фронтенд, если целевой сайт блокирует хотлинкинг или отдаёт жесткие CORS-заголовки/Cloudflare-защиту.
- **Деплой:** Существующий VPS (`ja4.ru`).

### Frontend
- **Интерфейс:** Простая HTML-страница с минимальным JS (без тяжелых SPA-фреймворков вроде React/Vue для простоты поддержки).
- **Стилизация:** Tailwind CSS (через CDN) или лаконичный Bootstrap.
- **Галерея:** Плитка превью с чекбоксами и горячими клавишами.
- **Фильтры и поиск:** По дате загрузки (`/uploads/YYYY/MM/`), по странице размещения, по паттерну имени файла, а также по статусу разбора.

## Функциональность

### 1. Сканирование сайта

**Вход:** URL сайта.

**Источники обхода** (пробовать по очереди, не полагаться только на один):
- `sitemap.xml` / `sitemap_index.xml`
- *Fallback:* Обход по внутренним ссылкам с главной страницы (лимит глубины/страниц конфигурируется).

**Извлечение изображений для каждой найденной страницы:**
- `<img src>`, `data-src`, `data-original` (lazyload-атрибуты)
- `<picture><source srcset>`
- `background-image` в inline-стилях
- **Фиксация в БД:** URL картинки, URL страницы (где встречается), дата (по структуры URL `/uploads/YYYY/MM/`, если применимо).

---

### 2. Структура БД (SQLite)

Каждая найденная картинка сохраняется в SQLite со следующей структурой:
- `id` — Уникальный ID
- `site_url` — Домен проверяемого сайта
- `image_url` — Прямой URL изображения
- `page_url` — Страница, где обнаружена картинка
- `status` — Текущий статус разбора:
  - `NEW` — Новая, еще не просмотрена (по умолчанию)
  - `KEEP` — Легитимная, оставить
  - `DELETE` — Отмечена к удалению
- `created_at` — Дата первого обнаружения картинки
- `last_seen_at` — Дата последнего обнаружения (при повторном сканировании обновляется автоматически)

**Уникальный ключ:** `(site_url, image_url, page_url)`. При повторном сканировании вместо вставки нового дубликата выполняется upsert: обновляется только `last_seen_at`, а `status` **не перезаписывается** (сохраняется решение человека). Если картинка при повторном скане не найдена — её строка в БД остаётся как есть (удаления из базы не происходит).

---

### 3. Визуальный отбор (UI/UX)

- **Плиточная галерея:** Карточки превью со статусом и чекбоксом, **загружаются постранично** (50–100 карточек за раз). Полный список не рендерится в DOM сразу, чтобы избежать зависаний при тысячах картинок.
- **Фильтрация:** По дате загрузки, по странице размещения, по паттерну имени файла, по статусу разбора (`NEW` / `KEEP` / `DELETE`). Фильтры применяются на бэкенде (SQL `WHERE` + `LIMIT/OFFSET`), не на клиенте.
- **Пакетное выделение (Массовые операции):**
  - Кнопка *«Выбрать все на странице»* (только видимые карточки текущей страницы).
  - Выделение диапазоном через `Shift + Клик` (кликнул первую, зажал Shift, кликнул 10-ю — выделились все между ними).
  - Кнопки быстрых действий: *«Отметить выделенное как KEEP»*, *«Отметить выделенное как DELETE»*.
- **Сохранение состояния:** Все клики (выделение, смена статуса) сразу сохраняются в SQLite через AJAX-запросы. Можно закрыть браузер и продолжить с этого же места в любой момент.

---

### 4. Генерация списка и экспорт на удаление

- Экспорт отмеченных записей со статусом `DELETE` в `.txt` — **один URL на строку**, совместимый с существующим `remove-images.php`.
- Готовая команда для копирования в буфер обмена (одна кнопка → скопировано в clipboard).

---

### 5. Поиск по множественным источникам (Расширяемость)

Паттерны источников оформляются как отдельные модули-чекеры (`checkers`), которые можно подключать по мере необходимости:

| Источник | Что проверяет | Статус v1 |
|---|---|---|
| `post_content` | Прямой `<img>` в тексте записи/страницы | Реализовано в `remove-images.php` |
| Featured image | `_thumbnail_id`, с нормализацией имени файла (срез суффикса `-WxH`) | Реализовано |
| Термин-мета (категории) | `wp_termmeta` — обложки категорий/тегов | Известен паттерн (в разработке) |
| Опции темы (Кастомайзер) | `wp_options` (`theme_mods_*`) | Известен паттерн (в разработке) |
| Хардкод в теме | Прямой grep по файлам темы (PHP-циклы) | Вручную через SSH |

---

### 6. Удаление (Выполняется НЕ инструментом, а вручную через WP-CLI)

Основной рабочий скрипт: `remove-images.php`
- `dry-run` по умолчанию (проверка без записи).
- `apply` как явный второй шаг для применения изменений.
- Обязательная поддержка флага `--skip-plugins` (защита от сломанных плагинов на старых сайтах).
- **Мягкое удаление:** `<img>` из контента убирается, featured image отвязывается, физический файл в медиабиблиотеке на первом этапе не трогается.

## Известные технические грабли (Учесть в коде)

1. **Суффиксы размеров WP:** WordPress хранит featured image как URL *оригинального* файла, но на странице выводится превью с суффиксом размера (`-150x150`, `-700x260` и т.д.). Сравнение имён файлов обязано срезать эти суффиксы регулярным выражением.
2. **Встроенный редактор WP:** При редактировании изображения через админку WP добавляет суффикс `-eXXXXXXXXXXXXX` к файлу на диске, при этом `guid` в БД остаётся старым. Сравнивать нужно по полю `_wp_attached_file`.
3. **Префиксы БД:** Разные сайты — разный префикс таблиц (не всегда `wp_`).
4. **Падения WP-CLI:** Старые сайты часто падают из-за конфликтов плагинов, поэтому WP-CLI команды всегда запускаются с `--skip-plugins`.
5. **Кастомные PHP-циклы темы:** Картинка на странице архива/категории может выводиться кастомным кодом темы. Такие случаи определяются grep'ом по файлам темы.
6. **CORS и блокировки Hotlinking:** При показе картинок с чужого домена браузер может блокировать их загрузку. Все `<img>` в интерфейсе инструмента пропускаются через прокси бэкенда (`/proxy-image?url=...`).
7. **Сканирование и UI параллельно:** Фоновое сканирование (вставка/обновление записей в SQLite) и одновременное взаимодействие пользователя с галереей на одной базе могут конфликтовать. SQLite в WAL-режиме (см. раздел "Архитектура") решает это: читающие транзакции (UI) не блокируют пишущие (сканирование) и наоборот.
